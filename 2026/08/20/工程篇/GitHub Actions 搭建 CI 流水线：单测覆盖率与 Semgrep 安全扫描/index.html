GitHub Actions 搭建 CI 流水线：单测覆盖率与 Semgrep 安全扫描

发表于2026-08-20|更新于2026-08-20|工程篇
|阅读量:

最近在补 Vibe Coding 方向的工程闭环，动手搭了一个最小 Demo 仓库，把 lint → 单测覆盖率门禁 → Semgrep SAST → PR 合并门禁 整条链路跑通。踩了不少 GitHub Rules 的坑，整理成文备忘。

Demo 仓库：vibe-coding-ci-demo

一、CI 是什么，配置写在哪

CI（Continuous Integration，持续集成） 的核心就一句话：每次 push 或开 PR，自动跑检查，尽早发现问题。

很多人第一次接触时会疑惑：CI 是写在代码库里，还是在 GitHub 网页上配？

答案是 两者配合：

位置 放什么
代码库 package.json 脚本、测试配置、.github/workflows/ci.yml
GitHub 平台 何时触发、分支保护、required checks

五、Semgrep：SAST 静态安全扫描

SAST 是什么

SAST = Static Application Security Testing，不运行程序，只分析源码找漏洞模式：硬编码密钥、eval、SQL 拼接、XSS 等。

AI 生成的代码常见问题：能跑、测试能过，但有安全洞。SAST 在 merge 前自动拦截已知危险模式。

六、GitHub 分支保护：我踩过的坑

这是本次学习里花时间最多的部分。GitHub 现在推荐用 Rulesets（规则集），和传统 Branch protection 类似，但更容易配错。

坑 1：目标分支选了「所有分支」

规则作用到 所有分支 + 开启 限制更新（Restrict updates） + Bypass 名单为空

→ feature 分支也 push 不了，报错 Changes must be made through a pull request

正确做法：规则只保护 main，feature 分支应能自由 push。

坑 2：「限制更新」导致 PR 也 merge 不了

CI 全绿，仍显示：

原因：限制更新 表示只有 Bypass 名单里的人能更新该分支，而 merge PR 本质上也是更新 main。

个人 Demo 推荐：

规则 是否开启
合并需要 PR 开（禁止直接 push main）
需要通过状态检查 开（选 quality check）
限制更新 关（否则 merge 也被拦）

坑 3：Review required

开了「最近可审查推送需要批准」，个人仓库里自己批不了自己，会一直卡在 Review required。

个人练手：Required approvals 设为 0，或关掉「最近推送需批准」。

坑 4：Status checks 列表为空

刚配规则时，「需要通过状态检查」里搜不到任何 check。

原因：GitHub 只列出已经跑过的 check。需要先 push 并开 PR，等 Actions 跑完一次，再回来添加 quality。

这三个不用勾

Settings 里还有：

  • Require code scanning results
  • Require code quality results
  • Restrict code coverage

这是 GitHub 原生 Code Scanning / Code Quality 能力，和 Actions 里跑 Semgrep + Vitest 不是一回事。当前 Demo 用 Require status checks → 选 quality 即可。

十、总结

  1. CI 配置在代码库，.github/workflows/ci.yml + package.json 脚本；门禁策略在 GitHub Settings。
  2. 覆盖率阈值 和 Semgrep 让 AI 生成代码有量化、可重复的验证闭环。
  3. Rulesets 目标分支只保护 main，别开「所有分支」+「限制更新」，否则 push 和 merge 都会翻车。
  4. Status checks 要等 CI 跑过一次才能选；选 job 名 quality 即可。
  5. Semgrep 用 brew / pip 装，别用 npm 占位包。
